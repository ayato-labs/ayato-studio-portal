# Ayato Studio 全体設計思想

本プロジェクトは、**「運用コスト極小」「耐障害性最大（DDoS耐性）」「自律型パブリッシング」**の3原則を極限まで追求するインテリジェンス・ハブ・アーキテクチャです。

---

## 1. ゼロ・コンピューティングとエッジ配信（静的化）

- **思想背景**:
  一般的な動的CMS（WordPressなど）やフル動的SSRサーバーは、DBアクセスとHTMLレンダリングをリクエスト毎に行うため、脆弱性攻撃やDDoS（分散サービス妨害）攻撃に極めて脆弱です。また、サーバーの常時維持による金銭的コストがかかります。
- **解決方針**:
  ポータル側（`ayato_studio_portal`）は、**「完全な静的サイト（SSG: Static Site Generation）」**として設計します。ユーザーのリクエストに対しては、サーバーレスのエッジサーバー（Cloudflare Pagesなど）に事前ビルドされたHTML/JSのみを返します。
  - Webサーバーを持たないため、リクエストに対するバックエンド演算処理がなく、DDoS攻撃によるサーバーダウンは構造的に発生しません。
  - Supabaseデータベースへのアクセスは、フロントエンドからは必要最低限の「Anon Keyによる読み取り専用ポリシー（Row Level Security: RLS）」に限定し、データの改ざんは一切受け付けないセキュリティを敷きます。

---

## 2. 自律型トリガーチェーン（Reporter & Portalの協調）

- **動的データの静的同期**:
  静的サイトでありながら最新ニュースや論文情報を維持するため、以下の自律型プッシュパイプライン（バッチ駆動の再構築）を採用しています。
  ```mermaid
  graph LR
      Cron[Cloud Scheduler] -->|1日2回起動| Reporter[ayato_reporter]
      Reporter -->|1. 新規AI論文・ニュースを収集・分析| DB[(Supabase DB)]
      Reporter -->|2. techプラグイン完了時のみトリガー送信| GH[GitHub Actions]
      GH -->|3. ポータルを再ビルド/デプロイ| Edge[Cloudflare Pages]
  ```
- **リビルド最適化の原則**:
  - レポーターが「AI＆半導体（`tech`）情報」を新しく処理したときのみ、GitHubへのリビルドイベントを送信します。
  - 金融・エネルギーなどの別系統エンジン実行時（または何らかの自動テスト時）には、無駄なビルドによるリソース消費を防止するため、トリガーは送信しないロジック（`skip_rebuild`）を徹底します。

---

## 3. 日本語・AI特化のインテリジェンス価値

- **英語情報の切り捨てと国内フォーカス**:
  英語圏の一次情報はノイズが多く、また国内のユーザー（エンジニア・ビジネスリーダー）がスキマ時間で効率よく読むには不向きです。そのため、本システムは「日本語で超速要約を届けること」に極限までフォーカスしています。
- **Gemini APIコストの最小化**:
  不要な多言語翻訳（英語レポートの並行生成など）は排除し、1回のアグリゲーションあたりのGemini APIトークン消費量を極小化しつつ、高品質な要約を生成するプロンプト設計を徹底します。
