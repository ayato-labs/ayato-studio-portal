# Ayato Studio: Cloudflare & GitHub Actions 統合デプロイ・リリース戦略

本プロジェクトは、取得済みの独自ドメイン `ayato-studio.ai` を用い、**「Cloudflare Pages」**と**「GitHub Actions」**を統合した全自動パブリッシングシステムを採用しています。

---

## 1. デプロイメント・アーキテクチャ

本システムのデプロイメント構造は以下の通りです。

```mermaid
graph TD
    Repo[ayato_reporter (GCP Run Job)] -->|1. techエンジン収集・分析完了| GH_API[GitHub API (repository_dispatch)]
    GH_API -->|2. rebuild-portal イベント検知| GH_Workflow[portal/.github/workflows/deploy.yml]
    GH_Workflow -->|3. 静的ファイルをビルド & Pagesへプッシュ| CF_Pages[Cloudflare Pages (Edge)]
    CF_Pages -->|4. CDN経由で即時配信| User[ユーザー (ayato-studio.ai)]
```

### アーキテクチャ構成要素

| 構成 | 技術・サービス | 役割 |
| :--- | :--- | :--- |
| **ホスティング基盤** | **Cloudflare Pages** | 世界200拠点以上のグローバルエッジネットワーク。極小の静的フェッチレイテンシとネイティブなDDoS保護を提供。 |
| **自動ビルドトリガー** | **GitHub Repository Dispatch** | `ayato_reporter` でのAI・半導体（`tech`）情報処理が完了したタイミングで、GitHub APIを介してポータルの再構築ワークフローを自律起動する。 |
| **認証とセキュリティ** | **Supabase Row Level Security (RLS)** | データベースとの接続情報をフロントエンドに持ちつつ、悪意ある書き込みを防ぐため、アノニマスロール（`anon`）に対しては `SELECT` 権限のみを厳密に付与。 |

## 2. リリース・自動ビルドの運用フロー

### 2-1. トリガーチェーンの動作フロー
1. **日次バッチ実行**: GCP Cloud Scheduler が午前5時および午後5時（日本時間）に `ayato_reporter` (Cloud Run Job) をトリガー。
2. **データの格納**: 収集された最新のAI論文・技術ニュースが Supabase へ保存される。
3. **リビルド指示**: `ayato_reporter` の実行終了時に `tech` エンジンが含まれていた場合、GitHub API的の `/dispatches` エンドポイントへイベント `rebuild-portal` を送信。
4. **静的生成 (SSG) の実行**: GitHub Actions が起動し、Next.js 16 アプリをビルド。Supabase から最新データを取り込み、すべてのページを静的HTMLとして出力（SSG/ISR）。
5. **エッジ配信開始**: 生成されたアセットが Cloudflare Pages へデプロイされ、全世界のエッジノードにキャッシュが瞬時に同期されます。

### 2-2. サブドメイン展開への拡張ロードマップ
- 将来的に「金融×AI」に特化したサブドメイン `finance.ayato-studio.ai` を稼働させる場合：
  - 同様の自律型デプロイパターンを適用し、メインドメインとは別個のリビルドトリガーを設定することで、システム間の結合を最小限に保ちつつ個別にSSG配信を行う。

---

## 3. トラブルシューティング & 運用保守

- **手動での再ビルド実行**:
  - もし情報の反映が遅れている場合、ポータルの GitHub リポジトリから Actions > `Deploy Portal` ワークフローを手動（`workflow_dispatch`）で起動することで、即時に最新のデータを取り込んだポータルサイトが再ビルドされます。
- **機密情報の管理**:
  - `ayato_reporter` から GitHub Dispatch を実行するための個人アクセストークン（`GH_PAT`）は、GCP Secret Manager にて安全に管理・インジェクションされています。
