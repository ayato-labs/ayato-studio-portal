# Ayato Studio: リポジトリ乱立の現状調査 & モノリポ（Monorepo）統合戦略書

## 1. 現状調査の結論（非効率の根本原因）

**結論: ご指摘の通り、リポジトリが過剰に分散（Polyrepo化）しており、開発速度と運用の効率を著しく阻害しています。**

### 現在の構造的歪み
`ayato-studio` ディレクトリ配下に、**5つの独立した Git リポジトリが混在** しています。

```
c:\Users\saiha\My_Service\programing\ayato-studio\ (← ルートはGit管理されていない！)
├── docs/ (← ADRやSQLマイグレーションがどのGitにも追跡されていない)
├── main-web-tech-ai/      [Git Repo 1: ayato-studio-portal]
├── ayato_reporter/        [Git Repo 2: ayato-reporter]
├── ayato_intelligence_hq/ [Git Repo 3: ayato_intelligence_hq]
├── sub-web-finance-ai/    [Git Repo 4: sub-web-finance-ai]
└── sub-web-game-ai/       [Git Repo 5: sub-web-game-ai]
```

### これにより発生している具体的な非効率:
1. **コミット・PR・リリースの重複作業（工数3倍）**:
   - 1つの機能（例: 全世界AIニュース）を追加する際、`ayato-studio-portal` と `ayato-reporter` の2箇所で別々にブランチ作成、コミット、プッシュ、PR作成、PRマージを行う必要があった。
2. **ドキュメント・設定の孤立**:
   - `docs/`（ADR、マイグレーションSQL、手順書）や `.secrets/` がルートにあるため、各サブプロジェクトのGitから追跡されない。
3. **同期ズレのリスク**:
   - DBスキーマを変更した際、バッチ側のコードとフロントエンド側の型定義が別々のリポジトリにあるため、バージョンの不一致やデプロイ順序のミスが起きやすい。

## 2. 理想的な構成: 「単一モノリポ（Monorepo）統合」

```
ayato-studio/ [単一のGitリポジトリ: ayato-studio]
├── apps/
│   ├── web/        (旧 main-web-tech-ai: Next.js ポータル)
│   └── reporter/   (旧 ayato_reporter: Python 3.12 バッチ)
├── docs/           (ADR, migrations, 設計書を一元管理)
├── packages/       (将来の共通型定義やスクリプト)
├── .github/        (全自動CI/CDワークフロー)
└── README.md
```

### モノリポ化のメリット:
- **アトミックコミット**: DBマイグレーション＋バッチ変更＋Web画面更新を、**たった1回のコミット＆1つのPRで同時に完結** できる。
- **デプロイの自動化**: GitHub Actions の `paths` フィルター（例: `paths: ['apps/web/**']` で Cloudflare デプロイ、`paths: ['apps/reporter/**']` で Cloud Run デプロイ）により、変更があった部分だけが独立して自動デプロイされる。
- **管理コスト激減**: ブランチの切り替えや `.git` トラブルが1リポジトリ分だけに半減する。

## 3. この分野の専門家5人による見解

### 専門家 1: モノリポ / プラットフォームアーキテクト（Google / Meta 型）
> **「個人〜少数精鋭チームでの分散リポジトリ（Polyrepo）は9割がデメリット。即座にモノリポに統合すべき。」**
> - **見解**: 巨大企業でさえTurborepoやNxなどのモノリポに回帰している。フロントとバッチが密結合して連携するSaaS基盤において、リポジトリを分ける理由は1つもない。1個のPRですべての連動をレビューできるのが圧倒的に正義。

### 専門家 2: インディーハッカー / ソロSaaSファウンダー
> **「週1本リリース（乱射）を目指すなら、リポジトリを行き来する時間は純粋なムダ。」**
> - **見解**: ソロ開発の最大の武器は「スピード」。リポジトリを分けると、ブランチ切り替え、PRマージ、シークレット管理の手間が掛け算で増える。`apps/` 配下にプロダクトを並べる単一リポジトリ構成にすれば、開発効率は3倍に跳ね上がる。

### 専門家 3: オープンソース（OSS）メンテナー
> **「スタンドアロン配布物と、Web基盤（Studio）を明確に切り分けよ。」**
> - **見解**: 個別に配布・インストールするツール（`ProjectCodeMap`, `Transform_MovieToText`）は個別リポジトリで公開し、Ayato Studio のポータル・バッチ基盤は1つの `ayato-studio` モノリポに集約するのが世界標準のベストプラクティス。

### 専門家 4: CI/CD & DevOps スペシャリスト
> **「GitHub Actions と Cloudflare / GCP の連携が最もシンプルになる。」**
> - **見解**: モノリポにすれば、GitHub Secrets（APIキーやトークン）を一括管理でき、リポジトリごとのキー更新漏れがなくなる。変更差分に応じた自動ビルドトリガーも1つのワークフローで一元管理できる。

### 専門家 5: ソフトウェアエンジニアリング倫理 / 減算の美学専門家
> **「『コードは負債』と同様に、『リポジトリ数も管理負債』である。」**
> - **見解**: 不要なリポジトリ境界を減算し、ひとつの秩序あるリポジトリに統一することこそが、認知負荷を最も減らし、長期的に持続可能なシステムを作る。
