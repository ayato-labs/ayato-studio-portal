## 始まりは「No such table: embedding_cache」
ある日の開発中、SharedMemoryServer(記憶管理MCP)が、自身の中心的な機能である `embedding_cache` テーブルを「存在しない」と報告してきました。

数分前まで元気に動いていたはずのAIが、突然記憶喪失になったのです。

### なぜ起きたのか?:環境変数とパス解決の罠
調査の結果、原因は極めて「現代的」なものでした。

1. **デフォルトパスの誤認**: コード上のデフォルトでは `.shared_memory/knowledge.db` を見に行く。
2. **環境変数の上書き**: しかし、システム環境変数に `MEMORY_DB_PATH` が設定されており、AIは全く別の場所にある `shared_memory.db` を読み込んでいた。
3. **認識のズレ**: AIは「正しいはずの場所」にある空のDBを開き、テーブルがないとパニックに陥っていた。

### 【技術資料】緊急修復用Pythonスクリプト:`fix_db_init.py`
実際に今回の「No such table(テーブル消失)」を解決した全コードです。ポイントは環境変数 `MEMORY_DB_PATH` を動的に解釈し、既存のスキーマを壊さずに不足分のみを補完する設計です。

```python
import asyncio
import os
import sys

# srcディレクトリをパスに通し、既存のモジュールを利用可能にする
sys.path.append(os.path.join(os.getcwd(), "src"))

from shared_memory.database import init_db

async def run_init():
    print("--- SharedMemoryServer DB Initialization ---")
    try:
        # 既存のテーブル構造をチェックし、不足分を作成
        await init_db()
        print("[Success] All tables checked and initialized (including embedding_cache).")
    except Exception as e:
        print(f"[Error] Failed to initialize DB: {e}")

if __name__ == "__main__":
    asyncio.run(run_init())
```
